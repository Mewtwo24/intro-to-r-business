AI Coding Workflow: Debugging

Debugging is not a separate activity from analysis. It is the process of comparing what the code did with what you intended, then narrowing the difference until you can make a justified change.

An AI assistant can accelerate debugging, but only if you give it precise evidence and keep control of the test.

Read the console in layers

Output

Printed output is the value an expression returned. Inspect whether it has the expected number of rows, columns, groups, units, and range.

A table with zero rows is output, not an error. It may mean a filter excluded everything.

Warnings

A warning means R completed an operation but wants you to review something. Common causes include missing values, failed type conversions, or values that could not be summarized.

Do not hide warnings just to make a report look clean. Decide whether the warning indicates a data-quality problem, an expected edge case, or a mistake.

Errors

An error means the requested operation did not complete. Read the final message and the function named near the top of the message. The error location is evidence about what R expected and what it received.

Messages

Messages are informational notices, such as package startup notes. They are not automatically failures.

A repeatable debugging loop

Step 1: Reproduce the smallest failure

Run the smallest section of code that still produces the problem. If a long pipeline fails, execute the import, then the first transformation, then the next. This tells you which step changes the data into an unexpected shape.

Step 2: Capture the evidence

Copy:

  • the exact error or warning;
  • the smallest code that reproduces it;
  • the output of names(data), dim(data), and str(data);
  • the expected behavior; and
  • any relevant package versions or file details.

Do not send only “it does not work.” The assistant needs the mismatch, not just the conclusion.

Step 3: Ask for explanation before a rewrite

Use a prompt that asks the AI to diagnose the cause, explain the relevant R concept, and propose the smallest targeted fix. Ask it not to rewrite unrelated code.

Step 4: Apply one change

Make one change in your own script. If you change five things at once, you will not know which change solved the problem or created a new one.

Step 5: Test the fix

Run the smallest reproducing example again. Then run the full analysis and compare the output with the original business requirement.

Step 6: Record the lesson

Write down what failed, why it failed, what fixed it, and how you verified the fix. A debugging note becomes a reusable review rule.

Common error patterns

Message or symptom What to investigate
object ‘x’ not found Misspelled name, wrong execution order, or object created in a different scope
could not find function Package is missing, not loaded, or the function name is wrong
undefined columns selected Column name does not match the data
non-numeric argument to binary operator Text, factors, or missing values are being used in arithmetic
replacement has length zero The object being assigned has no values or the index is empty
unexpected results with no error Wrong filter, join, grouping level, sign, unit, or denominator

The final row is particularly important in business analytics. Correct syntax can still produce an incorrect business result.

A debugging prompt template

I am working in R. Here is the smallest code that reproduces the issue: [paste code]. Here is the exact console output: [paste the complete message]. The data have these columns and types: [paste names and structure]. I expected: [describe expected behavior]. Please explain the likely cause in plain English, identify the specific line involved, suggest the smallest fix, and give me one test that will verify the fix. Do not rewrite unrelated parts of the code.

Reverse-engineer the proposed fix

When the AI suggests a change, ask:

  1. What assumption about the data does this fix rely on?
  2. Does it change the result or only suppress the error?
  3. Will it work for missing values, empty groups, and new categories?
  4. Does it preserve the business definition?
  5. What test would fail if the fix were wrong?

For example, if a tool suggests converting a character column to numeric, first inspect the values. Currency symbols, commas, text such as “unknown,” and empty strings may require different handling.

Debugging joins and summaries

Joins and summaries deserve extra attention because they can produce plausible but inflated results.

For a join, check:

  • the intended key;
  • whether the key is unique in each table;
  • the join type;
  • the number of rows before and after; and
  • whether unmatched records matter.

For a summary, check:

  • the observation unit;
  • the grouping columns;
  • whether the measure should be summed or averaged;
  • whether the denominator is weighted; and
  • whether missing values are excluded intentionally.

When the code runs but the answer is wrong

Use a result audit:

  • print the first and last rows;
  • count records before and after each filter;
  • inspect a few records manually;
  • compare a total with an independent calculation;
  • check the smallest and largest values;
  • test a known case; and
  • ask a stakeholder whether the metric matches their definition.

The best debugging question is often not “How do I fix this error?” It is “What would have to be true for this result to be correct?”
