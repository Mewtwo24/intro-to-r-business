Intro to R for Business Analytics

Syllabus and policies for an AI-partnered analytical computing course

Course identity

This is a rigorous introduction to R for students who want to make defensible business decisions from data. The course treats R as a language for computational thinking: you will represent a question, define a data contract, transform observations, inspect evidence, design a visual argument, and translate the result for a stakeholder.

Modern analysts do not need to type every line from memory. They do need to understand enough R to direct an AI assistant, recognize a plausible-looking mistake, test a result, and explain the business logic. We move from syntax memorization to computational orchestration and verification.

Prerequisites

No prior R programming is required. Students should be comfortable with percentages, averages, tables, and reading a short business case. Curiosity, careful note-taking, and a willingness to test assumptions matter more than prior coding experience.

Target competencies

By the end of the course, you should be able to:

  • read and write core R expressions involving names, vectors, tables, functions, and conditions;
  • construct dplyr and tidyr pipelines with explicit row grain, joins, missing-value rules, and denominators;
  • design ggplot2 graphics using the Grammar of Graphics and audience-appropriate annotation;
  • conduct EDA that checks distributions, missingness, outliers, and relationships before making a claim;
  • prompt Codex, Claude, ChatGPT, or another approved assistant using a schema-first specification;
  • debug AI-generated code by preserving errors, testing root causes, and applying small fixes;
  • write a three-sentence executive takeaway that is supported by the verified output.

Teaching philosophy

The course uses a Code Reviewer framework. Every script is treated as a proposal that must be inspected. The analyst is accountable for correctness even when an AI writes the first draft. We value reproducible evidence over clever syntax, explicit assumptions over confident prose, and useful questions over premature conclusions.

The learning loop is:

Business question → data contract → small code draft → run and inspect
→ verify grain, counts, denominators, and edge cases → visualize
→ translate for a stakeholder → record the decision and limitation

The AI Code Reviewer Standard

AI assistance is permitted and expected when used transparently. It cannot replace the following responsibilities:

  1. Define the population, time window, metric, and decision.
  2. Protect sensitive data by sharing schemas or synthetic examples instead of raw records.
  3. Check joins, grouping levels, missing values, zero denominators, duplicate keys, and date boundaries.
  4. Test generated code on a tiny hand-calculated example.
  5. Explain what the output means and what it does not establish.

Students should keep a prompt log for substantial work: the request, schema supplied, returned code, errors, changes, and acceptance tests. If the assistant’s suggestion is rejected, record why. Rejection is evidence of analytical judgment.

Module Primary concept Required readings Hands-on lab Target AI skill

2 Tidy transformation, joins, and reshaping R4DS: Data transformation Audit airquality or mtcars through a complete pipeline Schema-first prompting with explicit grain and acceptance tests
3 Visualization and exploratory analysis R4DS: Data visualization; R4DS: Explore Build a chart sequence and missing/outlier audit Iterative visual refinement without changing the claim
4 AI partnership and verification R4DS: Workflow; NIST AI RMF Debug a generated pipeline and produce a review log Request root-cause analysis, tests, and limitations
5 Guided business projects R4DS: Communicate Complete one project through Milestones 1–3 Delegate bounded subtasks while checking denominators and joins
6 Executive communication and reproducibility R4DS: The whole game Publish a verified brief and three-sentence takeaway Ask the AI to critique clarity without inventing evidence

Grading and mastery metrics

Category Weight What mastery looks like
Code accuracy and reproducibility 40% Clean-session execution, explicit assumptions, correct grain, and tests for edge cases
Visual clarity and honesty 25% Appropriate geometry, readable scales, useful labels, and no unsupported causal framing
Executive summary quality 25% Three sentences that state a finding, meaning, action, and limitation using verified values
AI process documentation 10% Prompt log, review notes, debugging evidence, and a clear acceptance decision

Grades reward reasoning that another analyst can inspect. A concise, well-tested pipeline is stronger than a long script that cannot explain its denominator.

Plain-English translation requirement

Every project must end with three sentences:

  1. Finding: what happened, for which population, and during which period.
  2. Meaning: why the pattern matters, using the defined metric.
  3. Action: what to investigate or do next, plus the most important limitation.

Avoid function names, unexplained acronyms, causal verbs, and numbers that do not appear in the verified output.

How to use this site

Start with Schedule and Milestones, then work through the R Foundations in order. The AI mastery pages provide reusable prompts and review patterns. The guided projects are specifications, not answer keys: use the sandbox to test your own draft, and keep your evidence with the final memo.
