AI Coding Workflow: Prompting

An AI coding tool can only make decisions from the context you provide. A strong prompt is a compact project brief: it identifies the data, the decision, the expected output, the tools, and the constraints.

The anatomy of a strong R prompt

1. State the business goal

Start with the decision or question, not with a function name.

Weak: “Group this data.”

Strong: “The sales director wants to compare quarterly revenue and order count across regions to decide where to focus coaching.”

The business goal gives the assistant a reason to choose an aggregation level and output format.

2. Describe the data contract

List the data frame name, column names, types, units, and a few example values. State whether each row is a transaction, customer, store-month, or another unit.

For example:

  • Data frame: transactions
  • One row: one completed order
  • Columns: order_id, order_date, region, customer_id, units, revenue, returned
  • order_date: Date
  • units: nonnegative integer
  • revenue: dollars before returns
  • returned: logical flag

This prevents the assistant from inventing column names or treating a transaction total as a customer-level measure.

3. Define the business terms

Words such as revenue, customer, growth, active, and best can have multiple meanings. Define them before asking for code.

Specify:

  • the reporting period;
  • whether returns, discounts, taxes, and shipping are included;
  • whether counts mean rows or unique identifiers;
  • the denominator for rates and percentages; and
  • how missing values should be handled.

4. Name the desired packages

If the assignment uses the tidyverse, say so. If the deliverable must use dplyr and ggplot2, say so. If the code should use only installed packages, say so.

For a Quarto or Shinylive lesson, include constraints such as:

  • use R;
  • use dplyr for wrangling and ggplot2 for plots;
  • write a complete self-contained example;
  • include comments and a plain-English explanation; and
  • do not use packages beyond shiny, dplyr, and ggplot2.

5. Specify the output

Describe the final artifact precisely:

  • one row per region;
  • columns for revenue, order count, and year-over-year growth;
  • sorted from largest to smallest growth;
  • a table and one chart; and
  • a three-sentence stakeholder interpretation.

6. Ask for assumptions and checks

Ask the assistant to list assumptions, identify possible edge cases, and suggest validation checks. This turns a one-shot answer into a reviewable draft.

Bad prompt versus good prompt

Bad prompt

Analyze my sales data in R and make a chart.

This prompt does not define the data, the period, the comparison, the package constraints, or the intended decision. A plausible response could still answer the wrong question.

Good prompt

I am preparing a regional sales review in R. The data frame is called transactions, with one row per completed order. It contains order_id, order_date, region, customer_id, units, revenue, returned, and order_year. order_date is a Date; revenue is in US dollars before returns; returned is TRUE for a fully returned order. Use dplyr and ggplot2. Keep orders from 2025 and 2026, exclude fully returned orders, calculate total net revenue and unique customer count by region and year, and calculate 2026 year-over-year revenue growth. Return a table with one row per region, sorted by growth, and a bar chart. Explain the pipeline, state assumptions, and include checks for missing regions, duplicate order IDs, and zero 2025 revenue.

The good prompt supplies a data contract, business definitions, packages, filters, metrics, output, and quality checks. Those details make the generated code easier to review.

Prompt patterns worth reusing

Ask for a plan before code

First restate the business question and propose the data transformations. Do not write code until you identify the observation unit, grouping level, measures, and assumptions.

Ask for a minimal reproducible example

If the real data are unavailable, create a small simulated data frame with the same column names and types. Make the example reproducible with a fixed random seed.

Ask for two explanations

After the code, explain each transformation twice: first in R terms and then in plain language for a nontechnical stakeholder.

Ask for a validation section

Add checks for row counts, missing values, duplicate keys, and the expected range of each calculated measure. Explain what a suspicious result would mean.

Ask for a constrained revision

Keep the existing output and variable names. Change only the calculation of net revenue and explain the change.

Narrow revision prompts reduce accidental changes elsewhere in the analysis.

A prompt is a specification, not a command to trust

A detailed prompt improves the first draft, but it does not guarantee correctness. Read the response as a proposed implementation of your specification. Compare every filter, join, calculation, and chart with the business definitions you supplied.

A useful habit is to keep three columns in your notes:

Prompt requirement Code evidence Test
Exclude returned orders A filter on returned Compare before and after row counts
Count unique customers distinct customer_id Compare with raw row count
Rank by growth descending growth column Inspect the first and last rows

This turns prompt quality into a practical review process.
